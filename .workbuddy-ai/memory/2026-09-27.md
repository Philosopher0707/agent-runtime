### Design points worth remembering

- **Classes are recorded, statuses are derived** (`refused > failed > partial > degraded
  > ok`). A recovered tool error stays `ok` with the class visible.
- **Retry policy lives in the tool boundary, not the loop.** That split is what makes
  replay exact — a recorded call replays as its recorded outcome sequence.
- **The trace records tool descriptors**, because they are inside every prompt hash.
  Without them replay silently diverged for any run whose registry had overrides.
- **A mutating tool cannot be registered** without a required `confirmation_token`, and
  the field is stripped from the advertised schema. The model cannot authorise a side
  effect; only the principal can.
- **Fail-closed guardrails** with the trust model made executable: the task is trusted
  (not scanned), tool output is not.

### Bugs I hit, and the generalisable lesson

1. **A step bound must gate *starting* a step, not finishing one.** `Budget.check()` ran
   after `add_usage`, so a `max_steps=1` run aborted before its one step's tool call.
   Split into `check(include_steps=...)`.
2. **`validation_alias` does not drive serialization.** A pydantic field needs `alias=`
   as well, or `model_dump` emits the field name and the round trip (which replay
   depends on) fails. Also: merging a dump with an override produced *both* spellings of
   the key — dump by alias so the two vocabularies cannot collide.
3. **Sandboxed environments deny writes to the system temp dir**, so `tmp_path` fixtures
   error out. `--basetemp=.pytest-tmp` in `pytest.ini_options` fixes it everywhere.
4. The `_stop(...).reason` pattern double-emitted `run_finished`; replaced with
   `_note_stop` (records, returns reason) so the loop finishes exactly once.

## Measured the injection-marker guardrail (open question #1)

Thinker said "ok do it" to settling the highest-value open question. Built the corpus and
the measurement *before* touching the rule, which is what produced a defensible
before/after.

| | before | after |
|---|---|---|
| benign false positives | 9/25 = **36.0%** | 0/26 = **0.0%** |
| recall (unambiguous) | 13/15 = 86.7% | 15/15 = **100%** |
| repo files a file tool would refuse | 10/46 | 2/46 |

Because the guardrail is fail-closed, the 36% meant **one legitimate run in three was
refused**. Dominant cause: the bare phrase "system prompt", which appears in any codebase
that has one — `AGENTS.md`, `runtime/loop.py`, `runtime/schemas.py` all tripped.

New: `evals/markers.py` (corpus + measurement engine), `scripts/measure_markers.py`,
`make markers`, `tests/test_marker_precision.py`, decision `0011`.

### The three things worth carrying forward

1. **The ablation flipped my conclusion.** After tiering, the ablation said the whole
   CONTEXT tier caught nothing — I nearly cut it. Asking "is that the markers or my
   corpus?" and adding three real attack shapes made it load-bearing. **A marker's measured
   contribution is a property of the corpus, not of the marker.** The mirror-image failure
   is inventing a payload *because* it justifies a marker; both look identical in a diff.
2. **A threshold is only a tripwire if the corpus makes it sharp.** A 5% budget on 26
   samples tolerates one failure, so defeating the proximity rule entirely passed the
   suite. Set the budget to 0% and added a long-document benign sample that only adjacency
   saves. Both tripwires now fire when the rule is removed.
3. **The comment explaining the false positive was itself a false positive.** My comment in
   `context/sanitize.py` places "system prompt" and "you must run" seven characters apart
   while explaining that they are not evidence. Left in place deliberately — rewording it
   would improve the metric without changing the limit.

One marker was cut as dead weight (`new_instructions_mention`); every marker is now
load-bearing, enforced by ablation. Open question #1 is answered and replaced with its
successor: whether a guardrail trip should refuse the *run* or only *withhold the result*.

Gates after: `make check` 211 passed, `make eval` 32/32, `make markers` ok, `make smoke` ok.

## Added CI, and made the gates the precondition rather than the aspiration

Thinker said "go step by step, follow the dependencies and provenance". CI first: the spec
says *"until `make eval` gates CI, no change may be claimed as an improvement"*, so every
claim I had made — including the 36% → 0% guardrail fix — was checkable only by me.

New: `make ci` (lock-check → check → eval → markers → smoke, stopping at the first failure),
`make lock-check`, `.github/workflows/ci.yml` (delegates to `make ci` and nothing else),
`tests/test_ci_contract.py` (16 tests asserting the delegation and the gate set).

**Each of the five gates was verified to fail before being trusted** — a stale lock, a
broken assertion, a wrong eval expectation, a dead marker, and an end-to-end regression each
turned `make ci` non-zero. Also verified `ci` stops at the first failure: with `markers`
broken, `smoke` never ran.

### Four things worth carrying forward

1. **A latent CI failure was in the Makefile, and looked harmless locally.** `UV_PYTHON ?=
   $(shell command -v python3.13 || ... || python3)` resolves to 3.13 here and would have
   resolved to 3.12 on a runner. Deleted the pin; `uv` reads `.python-version`.
2. **`make markers` exited 0 on a dead marker while its docstring claimed it couldn't
   disagree with the test.** The ablation was test-only. Found by testing the *gate*, not
   the code. This is the second time this session that two things which were supposed to
   agree had nothing comparing them.
3. **`cp` is aliased to `cp -i` here**, so my backup/restore silently declined and three
   mutated files persisted. Caught by `git status`. Use `command cp`, and verify the tree
   after any mutation experiment.
4. **`uv lock --check` doesn't write, but a later `uv run` re-resolves and does** — which is
   the concrete argument for `--frozen` in CI.

Gates after: `make ci` exit 0 — 227 tests (was 211), eval 32/32, markers ok, smoke ok.

Remaining spec gaps, in dependency order: **PII** (what may enter context, what must be
redacted before logging) and **rollback** (one command, documented, performed once).
