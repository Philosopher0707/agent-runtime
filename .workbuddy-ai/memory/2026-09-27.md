### Design points worth remembering

- **Classes are recorded, statuses are derived** (`refused > failed > partial > degraded
  > ok`). A recovered tool error stays `ok` with the class visible.
- **Retry policy lives in the tool boundary, not the loop.** That split is what makes
  replay exact — a recorded call replays as its recorded outcome sequence.
- **The trace records tool descriptors**, because they are inside every prompt hash.
  Without them replay silently diverged for any run whose registry had overrides.
- **A mutating tool cannot be registered** without a required `confirmation_token`, and
  the field is stripped from the advertised schema. The model cannot authorise a side
  effect; only the principal can.
- **Fail-closed guardrails** with the trust model made executable: the task is trusted
  (not scanned), tool output is not.

### Bugs I hit, and the generalisable lesson

1. **A step bound must gate *starting* a step, not finishing one.** `Budget.check()` ran
   after `add_usage`, so a `max_steps=1` run aborted before its one step's tool call.
   Split into `check(include_steps=...)`.
2. **`validation_alias` does not drive serialization.** A pydantic field needs `alias=`
   as well, or `model_dump` emits the field name and the round trip (which replay
   depends on) fails. Also: merging a dump with an override produced *both* spellings of
   the key — dump by alias so the two vocabularies cannot collide.
3. **Sandboxed environments deny writes to the system temp dir**, so `tmp_path` fixtures
   error out. `--basetemp=.pytest-tmp` in `pytest.ini_options` fixes it everywhere.
4. The `_stop(...).reason` pattern double-emitted `run_finished`; replaced with
   `_note_stop` (records, returns reason) so the loop finishes exactly once.
